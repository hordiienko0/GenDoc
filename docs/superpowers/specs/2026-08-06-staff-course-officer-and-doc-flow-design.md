# Курсовий офіцер + новий flow генерації документів у «Постійний склад» — Design

## Контекст

Розділ «Постійний склад» (`GenDoc/Views/Staff`, `StaffViewModel`) дозволяє додавати людей через загальний `RecipientEditWindow` і оформлювати документи через `StaffDocDialog` у трьох сценаріях: «Оформити відрядження», «Оформити відпустку», «Згенерувати документ» (ad-hoc/«в догонку»). Форма додавання людини вважається доброю за структурою, але:

1. «Курсовий офіцер» сьогодні не є окремою ознакою — це просто текст, який хтось вписує у вільне поле «Звання» чи «Посада». Немає ні поля, ні фільтра, ні мапінгу.
2. Після натискання «Згенерувати» в `StaffDocDialog` вікно просто закривається без жодного підтвердження, списку створених файлів чи способу їх відкрити/зберегти — на відміну від головного екрана «Генерація», де є підсумок і пропозиція відкрити папку.

## Частина A — «Курсовий офіцер» як окрема ознака

**Модель:** новий `bool IsCourseOfficer` на `Recipient` (схема — нова версія `DatabaseSchemaInitializer`, колонка `INTEGER NOT NULL DEFAULT 0`). Без окремого переліку ролей — проста ознака так/ні (за рішенням з брейнстормінгу), без нових шаблонів чи дій у «Швидкому оформленні» (там нічого не змінюється).

**Де ознака впливає:**
- `RecipientEditWindow` — чекбокс «Курсовий офіцер» у формі додавання/редагування.
- `StaffView` — фільтр за ознакою («Усі / Курсові офіцери / Інші») і колонка-позначка в таблиці «Постійний склад».
- Мапінг плейсхолдерів шаблонів (`TemplateFieldCatalog.RecipientFields`, `GenerationService.GetRecipientFieldValue`) — новий рядок «Курсовий офіцер» (значення «Так»/«Ні»), доступний для мапінгу `{{...}}` тегів у шаблонах документів так само, як інші поля людини.

## Частина B — Новий flow генерації в `StaffDocDialog`

**Проблема:** «Генерувати» → тиша → вікно закрилось. Немає підтвердження, немає списку файлів, немає способу відкрити чи зберегти результат деінде.

**Рішення:** `StaffDocDialog` стає двокроковим (однаково для всіх трьох сценаріїв — Відрядження/Відпустка/в догонку; різниця лише в наявності полів дат на кроці 1):

- **Крок 1 «Формування»** — те, що є зараз: дати (де застосовно), список шаблонів, підписант, ручні мітки, примітка, кнопки «Скасувати»/«Згенерувати».
- **Крок 2 «Документи»** — стає доступним і відкривається автоматично одразу після завершення генерації. Показує **всі** документи, коли-небудь згенеровані для цієї людини (не лише щойно створені) — перевикористовуючи існуючий архівний шаблон (`IDocumentArchiveService.QueryAsync`, стиль рядка з `ArchiveRowViewModel`), відфільтрований по `RecipientId`, з щойно згенерованими зверху. Кожен рядок: назва документа, дата, статус, дії **«Відкрити»** (як `DocumentArchiveService.OpenAsync` — тимчасова копія + відкриття системним переглядачем) і **«Зберегти як…»** (як `ArchiveViewModel.SaveAsAsync` — `SaveFileDialog`, копіювання вмісту в обрану користувачем теку). Підсумковий рядок зверху: «Згенеровано: N · пропущено: N · помилок: N».
- Футер кроку 2: «← Ще один документ» (повертає на крок 1 для цієї ж людини) і «Готово» (закриває діалог).
- Вкладка/крок 2 неактивна (сіра), поки генерація не відбулась хоча б раз у цій сесії діалогу.

Це замінює сьогоднішню поведінку `StaffViewModel.OpenDocDialogAsync`, яка після виклику `_staffService.GenerateDocumentsAsync`/`IssueDocumentsAsync` просто робить `RefreshAsync()` без жодного відображення результату.

## Самоперевірка

- Немає TBD/заглушок; обсяг обох частин узгоджений під час брейнстормінгу (проста ознака так/ні, без нових шаблонів; єдиний dialog-flow для всіх трьох сценаріїв, крок 2 показує повну історію документів людини).
- Узгоджено з існуючими патернами: `DatabaseSchemaInitializer` (без EF Migrations), Archive-стиль списку документів, `DocumentArchiveService.OpenAsync`/`ArchiveViewModel.SaveAsAsync` для дій з файлом.
