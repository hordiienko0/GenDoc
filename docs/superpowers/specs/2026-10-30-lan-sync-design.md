# Синхронізація бази між ПК без інтернету (брейншторм)

Дата: 2026-10-30. Гілка: `qa-2026-09-26`.

> **Замінено 2026-11-10** проєктом [2026-11-10-secure-sync-design.md](2026-11-10-secure-sync-design.md):
> ПК можуть бути в різних містах, тому мережеву частину (розділи 1, 7-10, частково 11-12 і етап 0)
> замінено пересилкою через інтернет. Облік змін, злиття, ідентифікатори, документи й флешка
> перенесені в новий документ.

## Задача

На 6 ПК, частина з яких у різних мережах, працюють з однією базою особового складу. Треба:

- **Рівноправні ПК.** На кожному своя зашифрована база й свої теки з документами. Немає «головного»
  комп'ютера: вимкнули будь-який - решта працює далі, а коли він повернеться, усе доженеться.
- **Чітка синхронізація.** Після обміну всі ПК мають однакові дані до останнього поля. Нічого не
  губиться мовчки, нічого не дублюється, а суперечки розв'язуються однаково на кожному ПК.
- **Стабільне швидке з'єднання.** Зміна на одному ПК з'являється на інших за секунду. Розрив Wi-Fi,
  сон ноутбука чи перезапуск програми відновлюються самі.
- **Без налаштувань мережі.** На інших ПК ніхто не вписує IP, порти, не лізе в брандмауер і роутер.
- **Безпечна передача.** Дані йдуть мережею лише зашифрованими, підключитися може тільки ПК, який
  явно прийняли в мережу. Жодної хмари й інтернету.

## Що є зараз і що це означає для синхронізації

| Факт у коді | Наслідок |
|---|---|
| База - файл SQLCipher поруч із програмою (`Data/DbPaths.cs`), пароль вводять при вході | На кожному ПК своя копія; синхронізуємо записи, а не файл |
| Ключі - `int Id` з `AUTOINCREMENT` у всіх таблицях | Два ПК незалежно створять запис №105 - зіткнення. Потрібні діапазони ID на кожен ПК (розділ 4) |
| Більшість моделей `ISoftDeletable` (`DeletedAt`, `DeletedBy`) | Видалення - це звичайна зміна поля, синхронізується просто |
| Жорсткі видалення: `DutyRosterService.SaveAsync` (`Services/Duty/DutyRosterService.cs:251`) стирає всіх учасників і клітинки графіка й створює заново; ще `ImportService.cs:392` (зброя), `GenerationService.cs:279, 549`, `CompletenessService.cs:701`, `TemplateBuilderService.cs:286` | Збереження графіка на двох ПК дасть два набори учасників. Графік треба перевести на зміну лише того, що змінилось; решті видалень потрібні «надгробки» (tombstones) |
| Каскадні видалення в SQLite (`OnDelete(Cascade)` у `AppDbContext`) | Дочірні записи видаляє база, EF про них не знає. Зміни треба ловити на рівні бази (розділ 2) |
| 7 масових `ExecuteUpdateAsync` (`IntakeService.cs:44, 47, 186, 189, 294, 306`, `OrgTreeService.cs:126`) | Обходять `SaveChanges`. Тригери бази їх зловлять, перехоплювач EF - ні |
| Вміст документів і шаблонів у базі: `Template`, `ExportTemplate`, `GeneratedDocumentContent`, `GeneratedGroupDocumentContent`, `DocumentAttachment` | Документи можна передавати разом із базою; великі блоби - окремою чергою (розділ 6) |
| `AppSettings` і `OrganizationSettings` - по одному рядку | Синхронізуються як звичайний запис, з полями-винятками |
| `AppSettings.DefaultOutputFolder` - шлях на конкретному ПК | Не синхронізувати: це налаштування ПК (розділ 5) |
| Унікальні індекси: кімната (`Building`, `Number`) серед невидалених, `UserSettings.UserProfileId` | Два ПК без зв'язку створять однакову кімнату - потрібне правило злиття (розділ 13) |
| Правила предметної області: `GeneratedDocument.IsCurrent` / `Version` (22 місця пишуть `IsCurrent`), дерево `OrgNode` (`ParentId`, `Path`), номер набору | Після злиття може бути дві «поточні» версії, цикл у дереві, два «Набори №31». Потрібен прохід виправлень після злиття (розділ 13) |
| Схема v31, міграції самої програми (`DatabaseSchemaInitializer`) | Синхронізуються лише ПК з однаковою версією схеми |
| Немає захисту від двох запущених копій програми; журнал SQLite звичайний (не WAL) | Два двигуни синхронізації на одній базі зіпсують стан. Потрібні один екземпляр і WAL |
| Екрани завантажують дані при переході; є `IMessenger` | Зміни з іншого ПК треба оголошувати повідомленням, щоб екран оновився |

Обсяг даних невеликий: робоча база зараз 0,4 МБ, тестова - 11 МБ. Усе вміщається в пам'ять і
передається локальною мережею за секунди. Це спрощує вибір: можна брати точні, а не «ощадливі» рішення.

## 1. Топологія

| Варіант | Плюси | Мінуси |
|---|---|---|
| А. Вузол-сервер, який обирають автоматично | Мало з'єднань | Вибори вузла, затримка при його зникненні, дві «половини» мережі можуть обрати два вузли |
| **Б. Кожен з кожним (mesh)** | Немає особливого ПК. Якщо A не бачить C, але обидва бачать B - дані підуть через B, бо B зберігає все | До N·(N-1)/2 з'єднань: 45 на 10 ПК - дрібниця |
| В. Постійний сервер на одному ПК | Найпростіше | Суперечить вимозі рівноправності |

**Рекомендую Б.** Канал між парою ПК відкривається зустрічним «стуком» обох (розділ 8). Якщо вийшло два
канали, лишається той, що відкрив ПК з меншим номером. Кожен ПК зберігає повний стан і віддає його
будь-кому, тож мережа сходиться, хай як ПК бачать одне одного. Ноутбук, що буває в двох мережах, сам
переносить зміни між ними (розділ 9).

## 2. Як ловити зміни

| Варіант | Що ловить | Ризик |
|---|---|---|
| А. Перехоплювач `SaveChanges` в EF | Лише зміни через EF | Пропускає каскади SQLite, `ExecuteUpdate`, сирий SQL. Будь-який новий `ExecuteUpdate` мовчки ламає синхронізацію |
| **Б. Тригери SQLite на кожну синхронізовану таблицю** | Усе, що змінює базу, хай як | Тригери треба генерувати й перебудовувати після міграцій |
| В. Періодично порівнювати всю базу з відбитком | Усе | Повільно, не видно, яке поле змінилось і коли |

**Рекомендую Б.** Механіка:

1. Для кожної синхронізованої таблиці програма генерує тригери `AFTER INSERT / UPDATE / DELETE` за
   моделлю EF. Генерація йде в кінці `EnsureInitialized`, тож нові колонки після міграції
   підхоплюються автоматично. Тригери перестворюються щоразу, тому вони завжди відповідають схемі.
2. Тригер оновлення пише рядок лише для колонок, що справді змінились
   (`WHEN OLD.col IS NOT NEW.col`). Запис іде в `_sync_pending(table, pk, column, seq)`.
3. Одразу після коміту двигун синхронізації ставить відкладеним змінам мітку часу (розділ 3) і
   переносить їх у метадані. Якщо програма впаде між цими кроками, `_sync_pending` лишиться, і мітку
   поставлять при наступному запуску.
4. Зміни, що прийшли з мережі, тригери ігнорують. Тригер викликає SQL-функцію
   `gendoc_sync_applying()`, яку програма реєструє на кожному з'єднанні (`SqliteConnection.CreateFunction`).
   Без функції тригер падає з помилкою. Тому писати в базу в обхід програми (наприклад, редактором
   SQLite) не вийде - і це добре.
5. Міграції схеми йдуть із вимкненим обліком: кожен ПК виконує ту саму міграцію сам і однаково,
   передавати її результат мережею не треба.

Тест-охоронець, як уже є `StaticResourceScopeTests`: кожна таблиця моделі або має тригери, або явно
позначена «лише цього ПК».

## 3. Модель злиття

| Варіант | Як працює | Вада |
|---|---|---|
| А. Останній запис рядка перемагає | Цілий рядок береться з новішої зміни | ПК-1 змінив телефон, ПК-2 адресу - одна зміна пропаде |
| **Б. Останній запис поля перемагає (CRDT LWW по колонках)** | Кожне поле має свою мітку; виграє новіша | Дві зміни одного поля - лишається новіша (стара видна в журналі) |
| В. Журнал операцій із ручним злиттям | Повна історія | Складно, повільно, людині незрозуміло |
| Г. Питати людину про кожну суперечку | Нічого автоматично | Десятки діалогів на день |

**Рекомендую Б** плюс прохід виправлень після злиття (розділ 13) і скриньку конфліктів для смислових
суперечок.

- **Мітка часу - гібридний логічний годинник (HLC):** час ПК + лічильник + номер ПК. При отриманні
  змін годинник підтягується до найбільшої побаченої мітки. Тоді порядок змін не залежить від того,
  чи правильно виставлено годинник Windows. Порівнюємо `(HLC, номер ПК)`, тож нічиїх немає, і всі ПК
  оберуть того самого переможця.
- **Захист від зламаного годинника:** якщо годинник ПК відстає чи спішить більш ніж на 5 хвилин
  відносно інших, синхронізація з ним стає на паузу з повідомленням «Виправте час на ПК-3».
  Інакше ПК з датою 2030 року вигравав би всі суперечки.
- **Метадані:** таблиця `_sync_meta(table, pk, column, hlc, device)`. Вона ж і є журналом: «дай усе
  новіше за моє» - це вибірка рядків з `hlc` більшим, ніж уже бачено від того ПК. Окремий журнал
  операцій, що росте вічно, не потрібен.
- **Що вже має кожен ПК:** вектор версій - найбільший HLC, побачений від кожного ПК. Обмін
  починається з векторів, і кожен шле лише різницю. Повторна доставка нічого не ламає: та сама мітка
  вдруге нічого не змінює.
- **Передаємо рядок цілком, зливаємо по полях.** Якщо в рядку змінилося хоч одне поле, іде весь рядок
  з мітками всіх полів (блоби - лише посиланням на відбиток, розділ 6). Інакше ПК міг би отримати
  кілька полів запису, якого в нього ще немає, і не зміг би його вставити через обов'язкові поля.
  Зайвий трафік при наших обсягах непомітний.
- **Видалення:**
  - М'яке видалення - зміна `DeletedAt`, ніякої окремої логіки.
  - Жорстке видалення - надгробок `_sync_tombstone(table, pk, hlc, device)`. Надгробок сильніший за
    одночасну правку: видалений запис не воскресає.
  - Надгробки старші за 180 днів, які бачили всі ПК, можна чистити.
- **Посилання на ще не отримані записи:** зміни йдуть у порядку HLC, тож батьківський запис зазвичай
  приходить раніше за дочірній. Пакет застосовується в одній транзакції з
  `PRAGMA defer_foreign_keys = ON`. Якщо батька таки немає (його поля пізніше переписали, і він
  потрапив у наступний пакет), рядок чекає в `_sync_parked` до приходу батька.

## 4. Ідентифікатори записів

| Варіант | Оцінка |
|---|---|
| **А. Діапазон ID на кожен ПК: `Id = номер_ПК × 2^24 + n`** | Модель, зовнішні ключі й код не змінюються; наявні записи лишаються як є |
| Б. Перейти на `Guid` | Переписати всі моделі, ключі, 200 місць у сервісах, тести. Відкинуто |
| В. Локальний ID + таблиця відповідностей | Складно й крихко. Відкинуто |

**Рекомендую А.**

- **Ємність:** `int` у C# - до 2 147 483 647. Блок 2^24 = 16,7 млн записів на таблицю на ПК; ПК
  №1-127. Наявні записи (ID менше 16,7 млн) - це блок 0 «до мережі», їх не чіпаємо.
- **Видача ID лише явна.** `AUTOINCREMENT` бере «більше за найбільший ID у таблиці»: щойно прийдуть
  записи ПК-7, ПК-5 почне видавати номери з блоку ПК-7. Тому перехоплювач EF ставить `Id` новим
  сутностям сам, з лічильника `_sync_idblock(table, next)` (лише цього ПК). Тригер вставки перевіряє,
  що новий ID лежить у блоці цього ПК, інакше `RAISE(ABORT)`: вставка в обхід перехоплювача
  (сирий SQL) не пройде.
- **Записи-зразки в майбутніх міграціях** отримують фіксовані ID у блоці 0, однакові на всіх ПК, бо
  кожен ПК виконує міграцію сам (розділ 2).
- **Номер ПК видає вже прийнятий ПК при приєднанні:** найбільший відомий номер + 1. Ризик: двох нових
  ПК одночасно приймають у двох розірваних частинах мережі, і вони отримають однаковий номер. Тоді
  синхронізація бачить два різні сертифікати з одним номером, зупиняє записи на новішому ПК і
  пропонує перенумерацію. Випадок рідкісний, але виявляється напевно.
- **Таблиця `DutyRosterCell`** має природний ключ (`MemberId`, `Date`, `Kind`) і нічого не потребує.

## 5. Що синхронізується, а що лишається на ПК

- **Синхронізується:** усі таблиці даних - особи, набори, дерево, кімнати, зброя й техніка,
  шаблони, пакети, архів документів, графіки, профілі користувачів (з хешем пароля BCrypt),
  налаштування користувачів, налаштування організації, журнал аудиту.
- **Лише на цьому ПК:**
  - `AppSettings.DefaultOutputFolder` - шлях, що існує лише тут;
  - `SchemaVersions`;
  - усі службові таблиці `_sync_*`;
  - номер і закритий ключ цього ПК.

  Поля «лише ПК» виключаються з тригерів і обнуляються в знімку для нового ПК.
- **Ключ мережі** однаковий на всіх прийнятих ПК, лежить у їхніх зашифрованих базах і передається
  лише прийнятому ПК (у знімку). Після вилучення ПК ключ змінюється (розділ 11).
- **Роль адміністратора мережі** (`UserProfile.IsNetworkAdmin`) синхронізується разом із профілями.
- **Журнал аудиту:** новий стовпець «ПК», щоб було видно, з якого комп'ютера зробили дію. Записи
  лише додаються, тож конфліктів не буває.

## 6. Документи: блоби й теки на диску

- **Окрема черга.** Вміст документів і шаблонів іде своєю чергою з нижчим пріоритетом. Спершу
  приходять дані (особа, запис архіву), потім файл, тож дрібні зміни не стоять за великим документом.
- **Адресація за вмістом.** Файл ідентифікується відбитком SHA-256 (`DocumentHashService` уже є).
  Однаковий вміст не передається двічі.
- **Передача шматками** по 256 КБ з докачуванням: обрив посеред великого файлу не починає все з
  нуля. `docx`/`xlsx` уже стиснуті - їх не стискаємо, метадані стискаємо (Brotli).
- **Вміст у базі - на всіх ПК, у фоні.** Записи архіву приходять одразу, вміст - слідом.
  - Документ відкривається навіть тоді, коли ПК, що його створив, вимкнений.
  - Обсяг невеликий: груповий рапорт - 23 КБ. Навіть 6 документів × 1000 осіб на рік - близько 150 МБ.
  - Якщо місця колись забракне, можна вмикати «вміст лише на вимогу» - тоді його тягнуть з мережі
    при подвійному кліку.
- **Теки на ПК - за вашою схемою:**
  - в архіві видно всі документи мережі з позначкою «у теці цього ПК» або «лише в базі»;
  - подвійний клік записує файл у «Документи» за тим самим відносним шляхом
    (`GeneratedDocument.FileName`) і відкриває його, тож структура тек на всіх ПК однакова;
  - кнопка «Отримати всі документи» дотягує вміст, якого ще бракує, і розкладає в теку все, з
    поступом «312 з 540».
- **Правки руками не перезаписуються.** Якщо файл на диску змінили руками (відбиток не збігається з
  тим, що програма записала востаннє), програма його не перезаписує. Нова версія лягає поруч як
  «… (з ПК-2).docx», а в архіві з'являється позначка.

## 7. Як ПК знаходять одне одного (без IP і налаштувань)

Шари від найшвидшого:

1. **Кеш останніх адрес.** При запуску програма одразу стукає за останніми відомими IP кожного ПК.
2. **Обмін адресами.** Підключені ПК розповідають одне одному, за якими адресами бачили решту. ПК з
   іншої підмережі стає відомим усім, щойно його побачив хоч один ПК (розділ 9).
3. **Широкомовний UDP** на кожен активний інтерфейс IPv4, порт 47820:
   - при запуску;
   - при зміні мережі (`NetworkChange.NetworkAddressChanged`);
   - після сну (`SystemEvents.PowerModeChanged`);
   - кожні 2 с, поки когось бракує.

   Цей пакет водночас відчиняє «вікно відповіді» брандмауера (розділ 8).
4. **Адресне простукування підмережі** - лише якщо 1-3 нікого не дали. Повільно (до 50 пакетів на
   секунду, одне коло на хвилину), щоб у мережі закладу це не виглядало як сканування.
5. **Адреса з запрошення.** Запрошення нового ПК несе адреси того ПК, з якого запросили (розділ 11).

Деталі:

- **Пізнавання.** ПК пізнають одне одного за відбитком сертифіката, а не за IP. DHCP може міняти
  адреси скільки завгодно.
- **Ідентифікатор мережі.** Пакет виявлення несе випадковий ID мережі, підписаний HMAC ключем мережі.
  Дві різні мережі GenDoc в одній будівлі (інший підрозділ) не змішуються й не бачать, хто є в чужій.
- **Віртуальні адаптери** (Hyper-V, WSL, VirtualBox, VPN) пропускаються. Перевага - інтерфейсам зі
  шлюзом. На цьому ноутбуці, крім Wi-Fi, є `vEthernet (WSL)` - його програма не чіпає.
- **Ізоляція клієнтів Wi-Fi** на точці доступу блокує все. Програма це розпізнає (своя адреса є,
  а сусіди не відповідають навіть на простукування) і пише зрозуміло: «Мережа не дає ПК бачити
  одне одного - скористайтеся флешкою або своїм роутером» (розділ 9).
- **Варіант для перевірки на етапі 0:** оголошення через вбудовану службу mDNS Windows
  (`DnsServiceRegister`). Тоді на запити відповідає сама Windows, і простукування майже не потрібне.

## 8. Брандмауер без прав адміністратора

Що відомо про ваші умови:

- Обліковий запис не адміністратор. Тож поставити правило брандмауера не можна, а кнопка «Дозволити
  доступ» у вікні Windows вимагає пароль адміністратора.
- Непрохані вхідні з'єднання заборонені в усіх профілях.
- Вихідні дозволені. Відповіді на власні вихідні UDP-пакети брандмауер пропускає - так працюють DNS,
  відеозв'язок, онлайн-ігри.
- Відповідь на свій широкомовний пакет пропускається 3 секунди (налаштування за замовчуванням).

Звідси принцип: **жоден ПК не чекає вхідних - обидва стукають одне до одного:**

1. ПК-А і ПК-Б дізнаються адреси одне одного (розділ 7).
2. Обидва шлють UDP-пакет одне одному з порту 47820 на порт 47820.
3. Брандмауер кожного бачить «свій» вихідний пакет до цього сусіда й пропускає зустрічний як відповідь.
4. Канал живе, поки ним щось іде. Пульс кожні 5 с не дає брандмауеру його забути (UDP-потік він
   забуває приблизно за хвилину тиші).

| Варіант | Оцінка |
|---|---|
| **А. Зустрічний стук по UDP (hole punching)** | Без адміністратора, без UAC, без налаштувань |
| Б. Правило брандмауера через UAC | Потрібен пароль адміністратора на кожному ПК, а його немає |
| В. Стандартне вікно Windows при першому запуску | Те саме: «Дозволити» вимагає адміністратора |
| Г. Один ПК з правами як точка зв'язку | Підсилення, якщо колись знайдеться такий ПК. Не обов'язково |

**Рекомендую А.** Якщо на якомусь ПК таки є адміністратор, програма запропонує поставити правило й
там (лише локальні адреси, лише `GenDoc.exe`). До такого ПК можна достукатися без зустрічного пакета,
тож з'єднання швидше. Але це не обов'язково.

**Що не відомо напевно** - перевіряємо першим етапом (розділ 17, етап 0) на ваших ПК у ваших мережах:

- чи пропускає брандмауер зустрічний стук для програми без правил;
- чи не ставить Windows правило «блокувати», якщо у вікні брандмауера натиснули «Скасувати»;
- чи не ріже мережа «education» обмін між клієнтами (ізоляція точок доступу);
- чи ходять пакети між різними підмережами закладу.

Сусіди в цій мережі є: таблиця ARP ноутбука бачить 10 адрес у 192.168.76-77.x. Це ознака, що обмін
між клієнтами можливий, але не доказ.

**Сторонні антивіруси-брандмауери** (ESET, Kaspersky тощо) можуть блокувати додатково. Діагностика
це показує: «ПК-2 видно, але він не відповідає - перевірте антивірус на ПК-2».

## 9. ПК у різних мережах і синхронізація через флешку

«Різні мережі» бувають трьох видів, і рішення в кожного своє:

| Вид | Приклад | Як синхронізуємо |
|---|---|---|
| Різні підмережі, між якими ходять пакети | Wi-Fi «education» і дротова мережа того самого закладу | Мережею. Широкомовні пакети підмережу не перетинають, тож адреси дають обмін адресами й запрошення (розділ 7), далі - той самий зустрічний стук |
| Різні роутери з NAT або мережі без зв'язку між собою | Інший корпус, інше місто, домашній роутер | Напряму неможливо без інтернету чи ретранслятора, а їх ви не хочете. Тому - ноутбук-кур'єр і флешка |
| ПК в одному місці, але мережа закладу заважає | Ізоляція клієнтів, блок UDP | За бажанням - свій недорогий роутер без інтернету лише для цих ПК: ні ізоляції, ні чужих пристроїв. ПК підключаються до нього звичайним Wi-Fi чи кабелем |

**Ноутбук-кур'єр.** Кожен ПК зберігає все й віддає будь-кому. Ноутбук, що вранці був у мережі А, а
вдень у мережі Б, сам привозить зміни з А в Б і назад, без жодних дій людини.

**Синхронізація через флешку** працює завжди, навіть без жодної мережі:

1. «Мережа» → «Синхронізація через флешку» → обрати ПК, з якими обмінюємося.
2. Програма пише на флешку файл `GenDoc-ПК3-2026-10-30.gdsync`. У ньому всі зміни, яких у тих ПК, за
   останніми відомостями, ще немає (за вектором версій з розділу 3), разом із вмістом документів.
3. На іншому ПК - «Імпортувати з флешки»: перевірка підпису, розшифрування, застосування. Повторний
   імпорт того самого файлу нічого не змінює.
4. Той самий ПК одразу пише на флешку відповідь зі своїми змінами. Один прохід флешки туди й назад -
   і обидва ПК однакові.

Захист файлу:

- шифрування AES-256-GCM ключем мережі (його мають лише прийняті ПК, у своїх зашифрованих базах);
- підпис ключем ПК-відправника: файл від чужого чи відкликаного ПК не імпортується;
- загублена флешка без ключа мережі нічого не дає.

## 10. Транспорт і стабільність

| Варіант | Оцінка |
|---|---|
| **UDP + надійна доставка (LiteNetLib, ліцензія MIT) + TLS поверх (`SslStream`)** | Працює із зустрічним стуком, без адміністратора. TLS стандартний, не саморобний: `SslStream` працює поверх будь-якого потоку, тож надійний канал UDP обгортаємо в `Stream` |
| TCP + TLS | Простіше, але потребує вхідних, тобто правила брандмауера. Лишається запасним для ПК, де правило є |
| HTTP/Kestrel, gRPC, SignalR | Ті самі вхідні, +20 МБ до exe |
| QUIC (`System.Net.Quic`) | Теж UDP, але зустрічний стук через msquic організувати складно |
| Власна надійна доставка поверх UDP | Можна, але LiteNetLib уже вміє повтори, порядок, розмір пакета, об'єднання дрібних пакетів |

**Рекомендую UDP + LiteNetLib + TLS.**

- **Один канал на пару ПК.** Усередині TLS - кадри: довжина (4 байти) + тип + тіло (MessagePack або
  `System.Text.Json` із жорсткими лімітами). Кадр не більший за 1 МБ, кадр більшого розміру = розрив.
- **Узгодження на початку:** версія протоколу, версія схеми, номер ПК, вектор версій. Якщо схеми
  різні, синхронізація стоїть з повідомленням «Оновіть програму на ПК-3».
- **Миттєвий поштовх.** Після локального коміту двигун за 100-300 мс шле різницю всім підключеним ПК.
  Раз на 30 с - звірка векторів: ловить усе, що могло проскочити.
- **Живучість каналу:**
  - пульс кожні 5 с (заодно тримає відчиненим брандмауер), 3 пропущені = розрив;
  - повторний стук з наростаючою паузою 0,5 → 1 → 2 → … → 10 с;
  - після сну й зміни мережі - одразу, без очікування.
- **Атомарність.** Пакет змін застосовується в одній транзакції SQLite разом з оновленням вектора.
  Обрив чи падіння посеред пакета нічого не псує, а повторна доставка безпечна.
- **Пріоритети в одному каналі:** спершу службові кадри, потім дані, потім шматки файлів.
- **Зворотний тиск.** Повільний ПК не роздуває пам'ять відправника: черга обмежена, відправник чекає.
- **База:**
  - `PRAGMA journal_mode = WAL` - екрани читають, поки синхронізація пише (SQLCipher це підтримує);
  - один екземпляр програми на ПК (іменований `Mutex`).
- **Цільові цифри:**
  - зміна видна на іншому ПК менш ніж за 1 с;
  - після блимання Wi-Fi зв'язок відновлюється менш ніж за 3 с;
  - новий ПК із базою 11 МБ готовий менш ніж за 10 с.

## 11. Безпека

### Від чого захищаємось

| Загроза | Захист |
|---|---|
| Хтось у мережі слухає трафік | TLS: усе зашифровано, ключі сеансу одноразові (ECDHE), тож записаний трафік не розшифрувати й пізніше |
| Чужий ПК видає себе за свій, перехоплення (ARP-спуфінг) | Взаємна перевірка сертифікатів: обидва боки звіряють відбиток зі списком довірених ПК. Сертифікати Windows і центри сертифікації не потрібні |
| Сторонній ПК хоче приєднатися | Приєднання лише за одноразовим запрошенням, яке може створити тільки адміністратор мережі (нижче) |
| Хтось підглянув або перехопив код запрошення | Код одноразовий, діє 72 години, прив'язаний до сертифіката ПК, з якого запросили. Адміністратор бачить, хто приєднався, і може відкликати |
| Інша мережа GenDoc у тій самій будівлі | Ідентифікатор мережі з HMAC у виявленні, окремий список довірених ПК |
| Вкрадений чи списаний ноутбук | «Вилучити ПК з мережі»: його відбиток відкликається, відкликання розходиться всім, і ПК більше ніхто не пускає. Ключ мережі змінюється, тож нові файли для флешки той ПК не прочитає |
| Зламаний пакет, спроба покласти програму | Ліміти кадрів і черг, тайм-аути, безпечна десеріалізація без `BinaryFormatter`, обмеження частоти підключень |
| Повтор старих пакетів | TLS не дає їх вставити; повторні зміни з тією самою міткою й так нічого не змінюють |
| Дані на диску | Кожна база - SQLCipher. Файли в «Документи» - звичайні `docx`, тому на кожному ПК потрібен BitLocker (це робить власник ПК) |

Від людини, якій уже дали доступ до мережі, синхронізація не захищає: у неї й так є вся база.
Тут допомагають лише журнал аудиту зі стовпцем «ПК» і відкликання.

### Ключі й приєднання

- **Сертифікат ПК.** При першому запуску кожен ПК генерує ключ ECDSA P-256 і самопідписаний
  сертифікат. Закритий ключ лежить у зашифрованій базі, у таблиці «лише цього ПК». Тому
  синхронізація можлива лише після входу в програму.
  - Особливість Windows: Schannel вимагає збереженого ключа, тож сертифікат перезавантажується
    через PFX - це врахувати в реалізації.
- **Список довірених ПК** - синхронізована таблиця `SyncDevices`: назва, номер, відбиток, хто й коли
  прийняв, коли відкликано. Хто довірений одному ПК, той довірений усім.
- **Адміністратор мережі** - позначка на профілі користувача (`UserProfile.IsNetworkAdmin`,
  синхронізується). Нею стає профіль, з якого створили мережу, тобто ваш. Лише він:
  - створює запрошення;
  - вилучає ПК;
  - передає чи додає роль.

  Решта профілів працюють з даними, але мережею не керують.
- **Запрошення - це код, а для іншої мережі ще й файл:**
  1. Адміністратор на будь-якому прийнятому ПК: «Мережа» → «Запросити ПК». З'являється код на 16
     символів, наприклад `K7QM-2XPA-9DF3-HW4R`. Його можна продиктувати телефоном - самому біля
     нового ПК бути не треба.
  2. На новому ПК: «Приєднатися до мережі» → ввести код. Частина коду - відбиток сертифіката ПК, що
     запросив. Тому новий ПК перевіряє, що говорить саме з ним, а не з посередником, і лише тоді
     передає решту коду (одноразовий токен).
  3. Новий ПК отримує номер, ключ мережі й знімок бази (розділ 12).
  4. Якщо новий ПК в іншій мережі без зв'язку - «Запросити ПК» → «Записати на флешку». Файл
     запрошення містить знімок бази, зашифрований ключем, отриманим з коду повільною функцією (PBKDF2).
     Новий ПК відкриває файл, вводить код і працює. Його сертифікат дійде до інших ПК із першою ж синхронізацією (мережею чи флешкою), і
     вони приймуть його, бо токен запрошення видав адміністратор.
  5. Код одноразовий: щойно ним скористався один ПК, другий з тим самим кодом не пройде.

  Якщо обидва ПК поруч, є простіший шлях: на обох екранах з'являється однаковий 6-значний код, звірений
  з даними TLS-з'єднання, і адміністратор тисне «Прийняти».
- **Чому не пароль бази як мережевий ключ:**
  - перехоплене рукостискання дозволяє перебирати пароль на своєму комп'ютері без обмежень;
  - зміна пароля на одному ПК розірвала б мережу.

  Пароль бази мережею не йде ніколи.
- **TLS 1.3** є в Windows 11. На Windows 10 Schannel має лише TLS 1.2 - тоді беремо
  ECDHE-ECDSA-AES-GCM, теж з одноразовими ключами. Інші набори шифрів вимкнено.

## 12. Перший запуск мережі й приєднання ПК

- **Перший ПК (з наявною базою).** «Мережа» → «Створити мережу». Що відбувається:
  - генерується ключ мережі;
  - ПК отримує номер 1;
  - профіль, з якого створили мережу, стає адміністратором мережі;
  - генеруються тригери й метадані для наявних записів (блок 0, мітка - момент створення мережі).

  Ні правил брандмауера, ні UAC.
- **Новий ПК (порожній).** Приєднання за запрошенням (розділ 11), далі знімок:
  1. Прийнятий ПК експортує копію бази через `sqlcipher_export` з одноразовим випадковим ключем і
     обнуляє в копії поля й таблиці «лише ПК».
  2. Копія й одноразовий ключ ідуть по TLS (або у файлі запрошення на флешці).
  3. Новий ПК відкриває копію цим ключем і одразу перешифровує її на пароль бази (`PRAGMA rekey`).
     Пароль один на всіх ПК, тож людина вводить той самий, яким входить на інших ПК.

  Пароль бази мережею не йде: технічно кожна база шифрується незалежно. Знімок швидший і точніший,
  ніж передавати записи по одному.
- **ПК, на якому вже є своя окрема база з даними.** У першій версії дві незалежні бази не
  зливаються: однакові ID там означають різних людей. Стара база відкладається як
  `gendoc.db.before-sync-РРРР-ММ-ДД`, ПК бере знімок мережі. Потрібне з неї переносять наявним
  імпортом з Excel.
- **Назва ПК** - за замовчуванням ім'я комп'ютера Windows, можна змінити.

## 13. Конфлікти й правила після злиття

Прохід виправлень запускається після кожного застосованого пакета. Він детермінований: кожен ПК
обчислює той самий результат з того самого стану. Тому ПК не перекидаються виправленнями одне з
одним, а однакові значення з різними мітками нічого не змінюють.

| Ситуація | Правило |
|---|---|
| Одне поле змінили на двох ПК | Виграє новіша мітка. Значення, що програло, - у «Журналі синхронізації»; у картці особи підказка «змінено на ПК-2 о 14:03» |
| Правка на одному ПК, м'яке видалення на іншому | Обидві зміни лишаються (різні поля): запис у кошику з правкою, його можна відновити |
| Правка на одному ПК, жорстке видалення на іншому | Видалення виграє |
| Дві однакові кімнати (будівля + номер) | Пізніша за міткою отримує « (2)» і потрапляє в скриньку конфліктів |
| Дві «поточні» версії документа для тієї самої особи й шаблону | Версії впорядковуються за (`GeneratedAt`, ПК, `Id`) і перенумеровуються 1..n, поточна - остання |
| Цикл у дереві підрозділів (ПК-1 переніс A під B, ПК-2 - B під A) | Переміщення з новішою міткою скасовується (вузол повертається на попереднє місце). `Path` після злиття перераховується, а не береться з мережі |
| Два «Набори №31» | Скринька конфліктів: перейменувати чи об'єднати |
| Ту саму людину (той самий особовий номер) додали на двох ПК | Скринька «схожі записи» з об'єднанням - окремий етап |
| Автозміна статусу наборів за датою (`IntakeService`) на кожному ПК | Однакові значення - тригер пише лише справжні зміни, мітки сходяться без конфлікту |
| Графік чергувань редагують на двох ПК | Після переробки `SaveAsync` клітинки зливаються поштучно за ключем (учасник, день, вид) |

## 14. Інтерфейс

- **Індикатор у рядку стану:**
  - «Мережа: 3 ПК, синхронізовано щойно»;
  - «Немає зв'язку з ПК-2 (12 хв), зміни в черзі: 5»;
  - «ПК-5 в іншій мережі, востаннє через флешку 3 дні тому»;
  - «Мережа не дає ПК бачити одне одного - що робити?».
- **Сторінка «Мережа»:**
  - список ПК (назва, номер, мережа чи флешка, коли бачили, скільки змін чекає);
  - для адміністратора мережі: «Запросити ПК» (код або файл на флешку), «Вилучити ПК», ролі;
  - «Синхронізація через флешку»: «Записати на флешку» / «Імпортувати з флешки»;
  - діагностика: інтерфейси, перевірка зв'язку з кожним ПК, різниця годинників.
- **Архів:**
  - позначка «у теці цього ПК» / «лише в базі» / «вміст ще йде»;
  - подвійний клік кладе файл у теку й відкриває його;
  - кнопка «Отримати всі документи» з поступом.
- **Скринька конфліктів** - смислові суперечки з розділу 13, з кнопками розв'язання. Звичайні
  суперечки полів зливаються автоматично й лише записуються в журнал.
- **Оновлення екранів.** Двигун шле `IMessenger`-повідомлення «змінено таблиці X, Y», і відкриті
  екрани перечитують дані. Якщо людина саме редагує картку, яку змінили на іншому ПК, - смужка
  «Запис змінено на ПК-2: оновити?». При збереженні поля зливаються за розділом 3.

## 15. Журнал і діагностика

- **Журнал синхронізації** - у `%LOCALAPPDATA%\GenDoc\logs`, поруч з `ErrorLog`: підключення, розриви,
  обсяги, помилки. Без персональних даних - лише таблиці, кількості, номери ПК.
- **«Зберегти діагностику»** - архів для розбору проблеми, теж без персональних даних.

## 16. Перевірка

- **Симуляція без мережі.** 3-5 ПК у пам'яті, випадкові дії, випадкові розриви, перестановка й
  повтор пакетів. Коли обмін закінчився, бази всіх ПК мають бути побайтно однакові (вивантаження таблиць),
  а правила з розділу 13 - виконані. Тисячі прогонів із фіксованим зерном, щоб падіння
  відтворювалось.
- **Збої.** Убити процес посеред пакета, посеред файлу, посеред знімка - після перезапуску все
  сходиться.
- **Тригери:**
  - кожна таблиця моделі покрита;
  - каскад SQLite створює надгробки (окремий тест);
  - `ExecuteUpdate` ловиться;
  - вставка без явного ID у синхронізовану таблицю падає.
- **Два процеси на одному ПК (loopback):** зустрічний стук, TLS поверх UDP, запрошення кодом, знімок,
  відкликання, звичайний профіль без ролі не може запросити.
- **Флешка:**
  - обмін туди й назад зрівнює два ПК;
  - повторний імпорт нічого не змінює;
  - файл від відкликаного ПК відхиляється;
  - зіпсований файл відхиляється без часткового застосування.
- **Ручна перевірка на ваших 6 ПК:**
  - Wi-Fi «education» і кабель;
  - дві різні підмережі;
  - вимкнення Wi-Fi на хвилину;
  - сон ноутбука;
  - ноутбук-кур'єр між двома мережами;
  - годинник збитий на 10 хвилин;
  - великий документ 20 МБ;
  - чужа мережа GenDoc поруч.

## 17. Етапи

Кожен етап завершений і перевірений сам по собі.

| Етап | Що робимо | Що після нього працює |
|---|---|---|
| 0. Польова перевірка мережі | Маленька перевірка (`GenDoc.exe --net-probe`) на 2-3 ваших ПК у ваших мережах: чи видно широкомовні пакети, чи проходить зустрічний стук без прав адміністратора, чи не ріже мережа обмін між клієнтами, чи ходять пакети між підмережами, затримка. Нічого не пише в базу | Знаємо напевно, чи працює мережевий шлях, чи потрібен свій роутер, чи лише флешка. Від цього залежить етап 4 |
| 1. Підготовка | Один екземпляр програми, WAL, `DutyRosterService.SaveAsync` - зміна лише того, що змінилось, поля «лише ПК», стовпець «ПК» в аудиті, роль адміністратора мережі | Програма як була, але готова до синхронізації |
| 2. Облік змін | Тригери, метадані, HLC, діапазони ID, надгробки, тести-охоронці | Кожна зміна має мітку, ID не зіткнуться |
| 3. Двигун злиття | Вектори, різниця, застосування, правила після злиття - на транспорті в пам'яті | Симуляція сходиться |
| 4. Мережа | Сертифікати, виявлення, зустрічний стук, UDP + TLS, запрошення, знімок | ПК в одній мережі синхронізують дані |
| 5. Флешка | Файли `.gdsync`, запрошення на флешці, ноутбук-кур'єр (працює сам після етапу 4) | ПК без зв'язку між собою теж синхронізуються |
| 6. Документи | Черга блобів, шматки, архів «у теці / лише в базі», подвійний клік, «Отримати всі документи» | Документи видно й відкриваються на всіх ПК |
| 7. Інтерфейс | Індикатор, сторінка «Мережа», скринька конфліктів, оновлення екранів | Можна віддавати людям |
| 8. (за бажанням) Оновлення по мережі | ПК з новішою версією пропонує свій exe іншим; встановлення з підтвердженням | Не треба носити exe флешкою |

Етапи 2-3 не залежать від мережі, їх можна робити паралельно з етапом 0.

## 18. Ризики

| Ризик | Що робимо |
|---|---|
| Новий код пише в базу в обхід тригерів | Неможливо: без функції `gendoc_sync_applying` тригер падає; тест-охоронець на кожну таблицю |
| Тригери відстали від схеми після міграції | Перестворюються при кожному запуску з моделі EF |
| Зіткнення номерів ПК | Виявляється при синхронізації, записи на новішому ПК зупиняються до перенумерації |
| Хтось вимкнув ПК на місяць і повернувся | Вектор версій бере все пропущене; надгробки живуть 180 днів |
| Збитий годинник | HLC + пауза при різниці понад 5 хв |
| Антивірус блокує | Діагностика називає ПК і причину |
| Мережа «education» ізолює клієнтів або ріже UDP | Виявиться на етапі 0. Запасні шляхи: свій роутер без інтернету, ноутбук-кур'єр, флешка |
| Windows після «Скасувати» у вікні брандмауера ставить правило «блокувати» | Перевіряється на етапі 0. Якщо так, програма прив'язує сокет так, щоб вікно не з'являлося, і пояснює, що тиснути |
| Простукування підмережі адміністратори закладу вважають скануванням | Простукування - лише коли нічого іншого не спрацювало, повільно; основні шляхи - кеш, обмін адресами, запрошення |
| Загублена флешка з `.gdsync` | Файл зашифровано ключем мережі; без прийнятого ПК його не прочитати |
| Обсяг метаданих | ~60 полів × 1000 осіб = 60 тис. рядків - для SQLite дрібниця; індекс за (`device`, `hlc`) |
| Різні версії програми на ПК | Синхронізація стоїть з повідомленням; етап 8 прибирає незручність |

## 19. Відкинуті варіанти

- **Спільна мережева тека з `gendoc.db`.** SQLite через мережеву теку псує файл при одночасному записі.
- **OneDrive чи будь-яка хмара.** Персональні дані виходять за межі ПК (див. коміт `ecbf94f`).
- **PostgreSQL чи SQL Server на одному ПК.** Є головний ПК, переписування міграцій, втрачається шифрування SQLCipher.
- **Тонкі клієнти через API.** Переписати 26 сервісів; без головного ПК ніхто не працює.
- **Готові бібліотеки:**
  - Dotmim.Sync - сервер має бути SQL Server/MySQL/PostgreSQL, злиття по рядках;
  - cr-sqlite - нативне розширення, сумісність із SQLCipher під питанням, проєкт майже не розвивається;
  - LiteSync - комерційний закритий код.
- **Пароль бази як мережевий ключ** - див. розділ 11.
- **Обов'язкове правило брандмауера (TCP-сервер на кожному ПК).** Потрібні права адміністратора, яких немає.
- **Ретранслятор в інтернеті** (як у месенджерів). Дані йшли б через інтернет, а ви цього не хочете.
